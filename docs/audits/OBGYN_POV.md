## Executive summary

**Bios's separately-encrypted reproductive database is the most institutionally remarkable single feature in the codebase from an Ob/Gyn standpoint, and it is not close.** The post-Dobbs threat model has produced multiple criminal cases in which menstrual-tracker data was used as evidence in abortion prosecutions (most prominently Burgess v. Nebraska 2022 — Facebook Messenger logs, but the architectural lesson generalises across the consumer-app category). Period-tracker apps with cloud-first architectures have been subpoenaed; some have complied. The class includes the largest-distribution products on iOS and Android. Bios's design — see [ReproductiveDatabase.kt](../../android/app/src/main/java/com/bios/app/data/ReproductiveDatabase.kt) — does seven things at once that, in combination, are without precedent in the consumer reproductive-health category:

1. **Separate SQLCipher database file** (`bios_repro.db`) with an **independent encryption key** stored in `EncryptedSharedPreferences` with `RequestStrongBoxBacked(true)` — see [ReproductiveDatabase.kt:190-201](../../android/app/src/main/java/com/bios/app/data/ReproductiveDatabase.kt#L190-L201). A compromise of the main DB key does not yield the reproductive DB.
2. **Independent destroy path** — see [ReproductiveDatabase.destroy()](../../android/app/src/main/java/com/bios/app/data/ReproductiveDatabase.kt#L92-L108) — that wipes the key, the DB file, the WAL, the SHM, and the journal in one call.
3. **Priority destruction on LETHE duress PIN** and dead-man's-switch — see [DataDestroyer.kt:42](../../android/app/src/main/java/com/bios/app/platform/DataDestroyer.kt#L42) — the reproductive DB is wiped *first*, before the main DB, on coercion.
4. **FHIR exporter hard-skips `WOMENS_HEALTH` by default** — see [FhirExporter.kt:83](../../android/app/src/main/java/com/bios/app/export/FhirExporter.kt#L83). The default share bundle cannot leak cycle data even if the owner forgets to filter.
5. **PDF report exporter rejects WOMENS_HEALTH at the type level** — see [PdfReportExporter.kt:52](../../android/app/src/main/java/com/bios/app/export/PdfReportExporter.kt#L52) (`require(focalMetric.domain != MetricDomain.WOMENS_HEALTH)`). The exporter cannot be misconfigured to produce a printable reproductive summary.
6. **Default 90-day retention** for the reproductive DB ([ReproductiveDatabase.kt:205](../../android/app/src/main/java/com/bios/app/data/ReproductiveDatabase.kt#L205)) vs. the longer main-DB retention. The forensic surface shrinks.
7. **Reproductive baselines are computed in-memory and stored in the main DB without raw values** — only statistical summaries cross the boundary. The raw BBT and onset readings never leave the isolated file.

A subpoena against a Bios owner who has used reproductive tracking can recover no plaintext cycle data without the device, the device PIN, and the reproductive-DB key — and on LETHE, the dead-man's-switch / duress-PIN paths render even physical seizure unhelpful if the owner has time to type the duress PIN. **This is the correct architecture for the threat model and it is implemented, not aspirational.** Every Tier A recommendation below assumes this floor is preserved.

The audit nevertheless surfaces real gaps. Ordered by clinical impact through the Ob/Gyn lens:

1. **No pre-eclampsia signature, despite all the substrate being in the box.** Pre-eclampsia is the #1 preventable cause of maternal mortality in the developed world, the diagnostic criteria (BP ≥140/90 after 20 weeks gestation + proteinuria *or* end-organ involvement — ACOG Practice Bulletin 222, 2020 update) are well-codified, and Bios has BP ingestion via [WithingsApiAdapter.kt](../../android/app/src/main/java/com/bios/app/ingest/WithingsApiAdapter.kt) (Withings BPM Connect / Core scale-and-cuff combination is in the standard consumer pricepoint), Samsung BP, and manual entry. The `HypertensionPatterns.hypertensionEmerging` pattern fires at ≥130/80 ACC/AHA in all owners, but **does not specialise to pregnancy** — and in pregnancy the threshold is different (140/90 marks gestational hypertension; 160/110 marks severe-range and changes the management algorithm), the meaning is different (pre-eclampsia is a multisystem disease, not just elevated BP), and the urgency is different (severe-range BP in pregnancy is a `URGENT`-tier event). The [PhysiologyState](../../android/app/src/main/java/com/bios/app/physiology/PhysiologyState.kt) enum already encodes `PREGNANCY_T1/T2/T3` and the gating mechanism (`excludedStates`) is in place; what is missing is a pregnancy-*specific* `preeclampsia_signature` that activates only in `PREGNANCY_T2 + PREGNANCY_T3` and combines BP threshold + neuro-symptom prompt + (when CGM is present) glucose dysregulation as a corroborator for atypical presentations. This is the single highest-yield maternal-health addition Bios can make, and it is one signal rule plus one URGENT escalation away.

2. **Pregnancy gating exists in the enum but most patterns don't read it.** [PhysiologyState.kt](../../android/app/src/main/java/com/bios/app/physiology/PhysiologyState.kt) ships `PREGNANCY_T1/T2/T3` and the [ConditionPattern.excludedStates](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L36) gate works — but only [cardiovascularStress](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L207) currently uses it. The class-2 patterns that will false-fire in pregnancy and are *not* excluded: [infectionOnset](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L127) (RHR is up by trimester 3 baseline — Mishra/Quer's +10% is *already met* by normal pregnancy physiology), [recoveryDeficit](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L339) (HRV is down in pregnancy as a baseline), [chronicInflammation](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L310) (RHR↑ + HRV↓ + skin-temp↑ is *defining* of late-second-trimester physiology), [metabolicDrift](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L242) (glucose tolerance shifts in pregnancy by design — this is the basis of the 24–28 week OGTT), [overtraining](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L210) (recovery patterns shift), and arguably [atrialFibrillationScreen](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L396) (pregnancy lowers the threshold for ectopy; benign sinus tachycardia of pregnancy is common). The current state will produce a pregnancy alert storm in the second and third trimesters, which trains owners to dismiss notifications — and Bios's URGENT tier loses signal value when it then needs to fire for pre-eclampsia. The fix is a one-line `excludedStates = PhysiologyState.PREGNANCY` addition to roughly six patterns, plus pregnancy-specific replacement patterns where appropriate.

3. **Postpartum has no model at all.** [PhysiologyState.POSTPARTUM](../../android/app/src/main/java/com/bios/app/physiology/PhysiologyState.kt#L35) exists ("first 6 months") and is read by `cardiovascularStress`, but **the first six weeks postpartum carry the highest maternal mortality burden of the entire pregnancy lifecourse** (CDC PMSS 2017-2019: 22% of pregnancy-related deaths occur 7-42 days postpartum, 11% occur 43-365 days postpartum). The high-mortality postpartum entities are exactly the ones a wearable can see early signs of: postpartum hemorrhage (sustained tachycardia + dropping BP), postpartum pre-eclampsia / eclampsia (BP rise persists or appears *de novo* up to 6 weeks postpartum, a particular MFM concern because owners and clinicians both lower their guard after delivery), peripartum cardiomyopathy (HR↑, exercise intolerance, sleep dyspnea — surfaces in the third trimester through 5 months postpartum), thromboembolic disease (VTE risk is 4-5× baseline through 6 weeks postpartum), and postpartum depression / postpartum psychosis (sleep architecture, HRV, activity all shift — see [mentalHealthCorrelate](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L424) and the psychiatry-audit cross-reference below). None of these have a Bios pattern. The `POSTPARTUM` state currently only *silences* alerts; it doesn't *redirect* the lens to the right ones.

4. **No gestational diabetes screening surface.** GDM affects ~7–10% of pregnancies (varies by population and screening strategy), and the standard of care is a 24–28-week oral glucose tolerance test (one-step 75g per IADPSG/WHO, or two-step 50g screen + 100g OGTT per ACOG). Bios has glucose ingestion via [Dexcom and Glucose adapters](../../android/app/src/main/java/com/bios/app/ingest/) and the [ScreeningCatalog.kt](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt) is the natural home for a "GDM screening due at 24-28 weeks" prompt when the owner has set `PREGNANCY_T2`. The CGM-during-pregnancy use case is a particular MFM-of-interest area for owners with pregestational diabetes (CONCEPTT trial 2017 — CGM in pregnancy reduces adverse neonatal outcomes); a pregnancy-specific CGM time-in-range pattern (TIR target in pregnancy is 63-140 mg/dL, tighter than the non-pregnant 70-180 of [GLUCOSE_TIME_IN_RANGE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L119)) would close the loop.

5. **Cervical and breast cancer screening cadences are present but mammogram lower-bound is contested.** [ScreeningCatalog.kt](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt) carries [cervical_cancer](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt#L73) (USPSTF 2018: 5-yr HPV co-test 30–65; 3-yr cytology 21–29 — cadence pinned to 60 months which is the lighter-burden HPV-era schedule) and [mammogram](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt#L66) (USPSTF 2024: biennial 40–74). These are fine as USPSTF defaults but the Ob/Gyn-society cadences differ meaningfully: ACOG recommends mammogram offering at 40 with shared decision-making and *annual* (not biennial) cadence option, ACS recommends starting at 45 with annual until 55 then biennial — and for cervical cancer ASCCP 2019 risk-based management has supplanted strict cadence tables in many practices when prior results are available. The catalog model can absorb this; no architectural change needed, only entries. **More importantly**: there is no `BRCA1/2 family history` or personal-history-of-DCIS modifier that would advance the mammogram start to 30 (high-risk MRI annually + mammogram annually per ACR/ACS for known BRCA carriers) — the primary-care audit flagged the same shape as gap §2.6 (family history / personal risk profile unmodeled).

6. **Menopause is structurally underserved despite Bios having the perfect substrate.** Vasomotor symptoms (hot flashes / night sweats) are detectable on skin-temperature + HR signature with reasonable sensitivity in the literature (Carpenter 2007, Thurston 2011 — sternal skin conductance is gold-standard, but wrist-temperature deviation + HR transient gives a workable proxy). Sleep disruption is the second most-cited menopausal symptom and Bios has [SLEEP_FRAGMENTATION_INDEX](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L87) and [WAKE_AFTER_SLEEP_ONSET](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L88). Bone-health is on the [DEXA biomarker line](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt#L101) (USPSTF 2018 ≥65). Mood shifts overlap with [mentalHealthCorrelate](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L424). All the inputs are present; **no `MENOPAUSAL_TRANSITION` state exists in [PhysiologyState](../../android/app/src/main/java/com/bios/app/physiology/PhysiologyState.kt), no `vasomotor_pattern` lives in ConditionPatterns, and the FSH / estradiol / AMH biomarker pathway is partial** ([ESTRADIOL](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L179) exists; FSH and AMH do not, both of which are the standard menopause-staging labs). NAMS 2022 hormone-therapy position statement increasingly anchors decision-making in the perimenopausal window; a pull-side "you are 47, your cycle log shows skipped cycles + hot-flash markers, your last FSH was N" surface would be exactly the kind of "answer when asked" instrument the manifesto describes.

7. **Cycle tracking exists and is well-built, but ovulation detection is single-modality (BBT-only).** [CycleInference.kt](../../android/app/src/main/java/com/bios/app/engine/CycleInference.kt) implements the classical Marshall 1968 / Barron & Fehring 2005 biphasic 3-day rule on BBT with optional menstruation-onset overlay. This is correct and conservative — but the FDA-cleared category leader (Natural Cycles, K200158 2018) uses BBT + LH-strip integration + cycle-length learning; the Apple Cycle Tracking surface uses wrist skin-temperature deviation overnight, which is what Bios's [SKIN_TEMPERATURE_DEVIATION](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L69) already captures but does not yet feed into cycle inference. HRV cyclic variation (Schmalenberger 2019) is referenced in [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L483) but not in ovulation inference itself. A multi-modal ovulation inference (BBT + overnight wrist temp + HRV phase + cycle-length history) would close the gap to the FDA-cleared category leaders without requiring an LH-strip add-on; the manifesto-clean version is "this is data, not contraception advice — for fertility-awareness contraception use a tool with clinical validation."

8. **PCOS, endometriosis, and adenomyosis have no first-class surface despite being the three highest-prevalence gynecologic diagnoses.** PCOS affects 8–13% of reproductive-age women, endometriosis 6–10% with diagnostic delay of 7–10 years (median, multiple cohorts), adenomyosis is increasingly recognised on MRI/HFUS in younger women than previously thought. Bios's substrate could meaningfully contribute: PCOS shows up as cycle irregularity (already partly covered by [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L475)) + insulin resistance ([HOMA_IR](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L169), [FASTING_INSULIN](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L168) — already in MetricType, no PCOS pattern wired) + hyperandrogenism ([TESTOSTERONE_TOTAL](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L178) present, but SHBG and free-androgen-index are not, and DHEA-S is not); endometriosis is principally diagnosed by symptom-cycle correlation (pelvic pain peaks with menses, dyspareunia, dyschezia) which is *exactly* what a pain-diary + cycle-phase pattern can support — Bios has [PAIN_SCORE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L79) and `CYCLE_PHASE` but no `pain_cycle_correlation` pattern; adenomyosis is dysmenorrhea + menorrhagia and the bleeding-quantification surface is absent.

9. **Contraception context is invisible to the engine.** Hormonal contraception meaningfully shifts HRV (depresses by 5–10% typical of combined OCPs — multiple studies), affects sleep architecture (progestins are sedating; some owners on cyclic regimens have predictable mood/sleep shifts in the placebo week), and abolishes the BBT thermal shift (no ovulation = no luteal-phase rise — [CycleInference.kt](../../android/app/src/main/java/com/bios/app/engine/CycleInference.kt) will simply emit no `OVULATORY`/`LUTEAL` for these owners, which is *correct* but uncommunicated). Copper IUDs increase menstrual flow and dysmenorrhea in the first 6–12 months. Depot medroxyprogesterone (DMPA) suppresses ovulation and causes characteristic amenorrhea + bone-density concerns long-term. **There is no `CONTRACEPTION_METHOD` annotation surface** that the pattern engine could read; it falls into the broader medication-annotation gap the primary-care audit flagged as §2.5. For Ob/Gyn this is high-leverage: a single self-reported "I am on combined OCPs" annotation lets the engine de-mystify the abolished BBT pattern, suppress mood-pattern false alarms in the placebo week if the owner desires, and gate fertility-awareness messaging correctly.

10. **Maternal mortality crisis structural alignment is real and unnamed.** US maternal mortality rates (CDC 2023: 22.3 deaths per 100,000 live births, ~3× UK / France / Germany) are not evenly distributed — Black women experience 49.5 deaths per 100,000, ~2.6× the white rate; American Indian / Alaska Native women experience 28.9; rural counties have 9% higher rates than urban (Hung 2017, JAMA). Multiple analyses (Bryant 2010, Howell 2018) cite access — not biology — as the primary driver: late prenatal care entry, fewer prenatal visits, lower postpartum follow-up. **Bios's architectural posture is structurally well-placed for this population**: free, no subscription gating (Manifesto Principle 3), API 28+ (works on older / cheaper devices common in underserved populations), no Play Services dependency (works on degoogled / non-GMS phones), fully offline (works on intermittent connectivity), low storage footprint, phone-sensor-only path for owners without a wearable. The project documentation does not currently name this — the primary stated rationale for the architecture is personal autonomy + LETHE threat model — but the *same architecture* is structurally relevant to the maternal-mortality-crisis access gap. This is parallel to the [Indigenous Americas audit's](INDIGENOUS_AMERICAS_POV.md) observation that Bios's architecture aligns with Indigenous data-sovereignty frameworks for reasons the project did not name. Worth surfacing.

The rest of this audit walks the strengths, the gaps, the tensions with manifesto principles, and the tiered recommendations.

## 2. Clinical gaps, ordered by impact

### 2.1 No pre-eclampsia signature

Pre-eclampsia is the single highest-impact addition Bios can make for maternal health, and the architecture already supports it.

**The clinical setup.** Pre-eclampsia is defined (ACOG Practice Bulletin 222, 2020; ISSHP 2018 criteria) as new-onset hypertension (BP ≥140/90 on two occasions ≥4 hours apart) after 20 weeks of gestation, with either proteinuria (≥300 mg/24h or P:Cr ≥0.3) *or* end-organ involvement (thrombocytopenia, renal insufficiency, hepatic enzyme elevation, pulmonary edema, neuro symptoms). Severe features add BP ≥160/110, severe thrombocytopenia, severe transaminase elevation, severe renal insufficiency, severe pulmonary edema, persistent headache or visual symptoms. **Severe-range BP in pregnancy is a hypertensive emergency** — the management algorithm is acute antihypertensive therapy within 30–60 minutes, often inpatient, and delivery planning regardless of gestational age once severe features manifest. Pre-eclampsia accounts for ~15% of US maternal deaths and the deaths are largely preventable.

**The Bios setup.** BP is ingested via [WithingsApiAdapter.kt](../../android/app/src/main/java/com/bios/app/ingest/WithingsApiAdapter.kt) and Samsung BP per [WEARABLES_AND_DETECTION.md](../WEARABLES_AND_DETECTION.md), and is manually enterable per [MetricType.kt:47-48](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L47-L48). [HypertensionPatterns.hypertensionEmerging](../../android/app/src/main/java/com/bios/app/alerts/HypertensionPatterns.kt#L62) fires at median ≥130/80 across multiple readings (ACC/AHA 2017 stage 1). [PhysiologyState.PREGNANCY_T1/T2/T3](../../android/app/src/main/java/com/bios/app/physiology/PhysiologyState.kt#L32-L34) is in the enum. The `severityFloor = AlertTier.URGENT` mechanism is in [HypertensionPatterns.kt:137](../../android/app/src/main/java/com/bios/app/alerts/HypertensionPatterns.kt#L137) for hypertensive urgency ≥180/120, and the [ConditionPattern.excludedStates](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L36) gate works. **Every component the pattern needs exists.**

**The recommendation.** Add a `preeclampsiaSignature` pattern in [HypertensionPatterns.kt](../../android/app/src/main/java/com/bios/app/alerts/HypertensionPatterns.kt) with three shapes:

| Shape | BP threshold | Gating | Severity floor | Suggested action text |
|---|---|---|---|---|
| `preeclampsia_gestational_htn` | median ≥140/90 across ≥3 readings spanning ≥2 days | `PREGNANCY_T2`, `PREGNANCY_T3` only | `ADVISORY` | "Sustained BP at or above gestational-hypertension threshold (140/90). Discuss with your obstetric provider — pre-eclampsia screening labs (CBC, comprehensive metabolic panel, urine protein) and a follow-up visit are the standard next step." |
| `preeclampsia_severe_range` | single ≥160/110 *or* median ≥160/110 across 2 readings | `PREGNANCY_T2`, `PREGNANCY_T3`, `POSTPARTUM` | `URGENT` | "Severe-range BP in pregnancy or postpartum is a hypertensive emergency. If accompanied by headache, visual changes, right-upper-quadrant pain, or shortness of breath, contact your obstetric provider or labor and delivery immediately. Otherwise re-check on a warm clean arm after 15 minutes — if still ≥160/110, contact your provider." |
| `preeclampsia_postpartum` | median ≥140/90 *or* single ≥160/110 | `POSTPARTUM` only | `ADVISORY` / `URGENT` respectively | "Postpartum pre-eclampsia can manifest up to 6 weeks after delivery, often without prior pregnancy hypertension. Contact your obstetric provider — postpartum pre-eclampsia is a diagnosis many patients and providers overlook." |

Postpartum pre-eclampsia is the specific clinical gotcha — it is the case where both the patient and the clinical team have "moved on" from the pregnancy mindset, and Bios is in a position to be the watchful instrument that doesn't move on. The literature support (Sibai 2012 — *Obstet Gynecol*; ACOG 2020 Practice Bulletin 222; SMFM Consult Series 33) is solid. The implementation is two new entries in `HypertensionPatterns.all`. This is the single highest-yield Ob/Gyn addition.

### 2.2 Pregnancy gating is structurally incomplete

The [PhysiologyState.excludedStates](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L36) mechanism exists but only [cardiovascularStress](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L207) reads it. Normal pregnancy physiology — extensively characterised across the obstetric literature (Sanghavi & Rutherford 2014, *Circulation*; Hunter & Robson 1992, *Br Heart J*) — includes:

| Trimester | RHR change | HRV change | Skin temp | Sleep | BP |
|---|---|---|---|---|---|
| T1 | +5–10 bpm | mild ↓ | slight rise | fragmentation | ~ baseline |
| T2 | +10–15 bpm | ↓ ~20% | +0.3–0.5 °C | improving | nadir, often −5/−10 |
| T3 | +15–20 bpm | ↓ ~30% | +0.3–0.5 °C | fragmentation, sleep apnea rising | returns to baseline; pre-eclampsia rises if present |

This physiology systematically false-fires the following Bios patterns:

| Pattern | Mechanism of false fire | Recommendation |
|---|---|---|
| [infectionOnset](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L127) | T2/T3 RHR is already +10–20 bpm; HRV is already depressed; skin temp is already +0.3–0.5°C. The Mishra/Quer thresholds (+10% RHR, HRV depression, +0.5°C skin temp) are *defining* of T2/T3 baseline | Add `excludedStates = PhysiologyState.PREGNANCY` *or* recompute the personal baseline within the trimester window (preferred — preserves infection detection in pregnancy, just against the pregnancy-shifted baseline) |
| [chronicInflammation](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L310) | RHR↑ + HRV↓ + skin-temp↑ over 1–2 weeks is normative T2 physiology | `excludedStates = PhysiologyState.PREGNANCY` |
| [recoveryDeficit](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L339) | HRV is structurally depressed in pregnancy; the "HRV below baseline for extended period" pattern fires by design | `excludedStates = PhysiologyState.PREGNANCY` |
| [metabolicDrift](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L242) | Pregnancy is *defined* by insulin-resistance shift in T2–T3; CGM CV rises and TIR drops by physiology, not pathology | `excludedStates = PhysiologyState.PREGNANCY` for the wearable trigger; replace with pregnancy-specific `gestational_diabetes_signature` (see §2.4) |
| [overtraining](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L210) | Reduced activity + HRV↓ + sleep changes match pregnancy by physiology | `excludedStates = PhysiologyState.PREGNANCY + POSTPARTUM` |
| [cardiorespiratoryDeconditioning](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L274) | Pregnancy activity reduction is normative | `excludedStates = PhysiologyState.PREGNANCY` |
| [sleepDisruption](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L158) | T1 nausea + T3 size discomfort + postpartum infant care all fragment sleep normatively | `excludedStates = PhysiologyState.PREGNANCY_T3 + POSTPARTUM` (T2 is often improved-sleep; don't blanket-exclude) |
| [atrialFibrillationScreen](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L396) | Pregnancy increases benign sinus tachycardia and ectopy frequency; the irregularity threshold needs to widen | Trickier — pregnancy *also* increases real arrhythmia incidence (peripartum cardiomyopathy considerations). Keep active but raise `thresholdSigma` for the irregularity rule in pregnancy state |

The `excludedStates` mechanism is the right primitive. The work is adding the field to the patterns. This is a single-PR change with clear test cases (the existing [PhysiologyStateGatingTest.kt](../../android/app/src/test/java/com/bios/app/PhysiologyStateGatingTest.kt) shows the test shape).

### 2.3 Postpartum has no replacement patterns

The first 6 weeks postpartum carry maternal mortality at a rate disproportionate to their duration. CDC PMSS 2017–2019: of pregnancy-related deaths, 22% occur 7–42 days postpartum and another 11% occur 43–365 days postpartum. The high-mortality entities are wearable-detectable:

| Postpartum entity | Detection substrate in Bios | Pattern to add |
|---|---|---|
| **Postpartum hemorrhage** (>1000 mL within 24h of delivery, or any bleeding causing symptomatic hypovolemia) | Sustained RHR rise + dropping BP (orthostatic), pallor markers absent | Beyond the acute window most owners are no longer in monitoring posture; pattern relevance is for delayed/secondary PPH (24h–6wk postpartum), where wearable could catch a sustained tachycardia escalation. Severity floor `URGENT` |
| **Postpartum pre-eclampsia / eclampsia** | BP rise + headache/visual symptoms prompts | Covered by §2.1 third row |
| **Peripartum cardiomyopathy** (PPCM) | New-onset HF symptoms 1 month before to 5 months after delivery; resting tachycardia, exercise intolerance, dyspnea, edema; BNP / echo for diagnosis | Wearable proxies: sustained RHR elevation outside pregnancy expectation + sleep dyspnea (nocturnal HR pattern) + reduced exercise tolerance. Add `ppcm_screen` pattern |
| **Venous thromboembolism** (DVT / PE) | VTE risk is 4–5× baseline through 6 weeks postpartum; symptoms localised | Hard to wearable-detect specifically (acute event), but pull-side risk-awareness surface is appropriate — "the postpartum 6-week window carries ~5× baseline VTE risk; one-sided leg swelling/pain or sudden shortness of breath are the symptoms to act on" |
| **Postpartum depression / postpartum psychosis** | Sleep architecture shifts (which are also normative with newborn care — false-positive risk is high), HRV, activity, mood-drift via W2F | [mentalHealthCorrelate](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L424) is close, but needs a postpartum variant that uses a different baseline (newborn-care sleep disruption is normative; the *signal* is mood + activity + HRV trending while sleep is sleep-of-the-newborn-window). Cross-reference psychiatry audit |
| **Postpartum thyroiditis** | TSH excursion 6 wk – 12 mo postpartum; tachycardia → bradycardia phase progression | [hyperthyroidSignature](../../android/app/src/main/java/com/bios/app/alerts/BiomarkerConditionPatterns.kt) and `hypothyroidSignature` already exist; a "postpartum thyroid screening" cadence prompt at 6 weeks and 6 months postpartum in [ScreeningCatalog.kt](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt), gated on `POSTPARTUM` state, closes the loop. ACOG recommends TSH at 6 weeks postpartum for symptomatic patients and for type 1 diabetes / known thyroid disease |

The postpartum window is the highest mortality-yield application of wearable monitoring in the entire Ob/Gyn lifecourse, and Bios is structurally well-placed for it (continuous monitoring, low-power, owner-asserted state, no Play Services dependency for postpartum patients on degoogled phones or low-tier hardware).

### 2.4 Gestational diabetes (GDM) is unaddressed

GDM affects ~7–10% of US pregnancies (population-dependent). Standard of care:

- **Screening cadence**: 24–28 weeks gestation for all (one-step 75g OGTT per IADPSG/WHO; two-step 50g screen + 100g OGTT per ACOG)
- **Early screening** at first prenatal visit if BMI ≥25 + risk factors (history of GDM, family history of T2DM, PCOS, ethnicity-stratified higher prevalence)
- **CGM in pregnancy** — CONCEPTT trial (Feig 2017, *Lancet*) demonstrated CGM in T1DM pregnancy reduced LGA, NICU admission, and severe hypoglycemia. CGM TIR target in pregnancy is 63–140 mg/dL, *tighter* than the non-pregnant 70–180 in [GLUCOSE_TIME_IN_RANGE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L119)

Recommendations:

1. **GDM screening cadence entry** in [ScreeningCatalog.kt](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt), gated on `PREGNANCY_T2` state, prompting at 24 weeks gestation. Owner asserts gestational age — Bios does not infer
2. **Pregnancy-tightened CGM TIR target** — when `PhysiologyState.PREGNANCY_T1/T2/T3` is active, the [GLUCOSE_TIME_IN_RANGE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L119) target shifts from 70–180 to 63–140. The [metabolicDrift](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L242) pattern in pregnancy reads this tighter target
3. **Postpartum T2DM screening** at 6–12 weeks postpartum for owners who had GDM — 50% of GDM owners develop T2DM within 10 years (Bellamy 2009 meta-analysis). Cadence entry in `ScreeningCatalog` gated on a `had_gdm` owner-asserted annotation

### 2.5 Ob/Gyn-society screening cadences differ from USPSTF defaults

[ScreeningCatalog.kt](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt) ships USPSTF v1, which is the right default. Ob/Gyn-society guidance differs on three reproductive-cancer entries enough to mention:

| Screening | USPSTF (in catalog) | ACOG / ACS / ASCCP | Recommendation |
|---|---|---|---|
| Mammogram | biennial 40–74 (USPSTF 2024) | ACOG: offer at 40, shared decision-making, annual cadence option; ACS: start 45, annual until 55 then biennial; high-risk (BRCA, prior chest RT, FHx) — annual MRI + mammogram from 30 | Add an "Ob/Gyn-society cadence" catalog variant; owner picks default (USPSTF / ACOG / ACS); BRCA/high-risk modifier requires the family-history surface from primary-care audit §2.6 |
| Cervical | 5-yr HPV co-test 30–65 (USPSTF 2018) | ASCCP 2019 Risk-Based Management — cadence varies by prior results, not by strict cycle. Current ACOG aligns with ASCCP | Catalog-level recommendation: keep USPSTF cadence as default but acknowledge in display that prior-result-anchored cadences may apply per provider |
| DEXA | postmenopausal ≥65 (USPSTF 2018) | ISCD/NAMS: postmenopausal <65 with risk factors (low BMI, FHx hip fracture, smoker, glucocorticoid, RA); FRAX-driven for the <65 cohort | Risk-factor entry surface — overlaps primary-care §2.6 |

The catalog architecture supports this — multiple `ScreeningCatalogEntry` lists with the same `key` can be selected by `RegionConfig` plus an owner-chosen society preference. The work is entry-level, not architectural.

### 2.6 Menopause and the perimenopausal transition

Menopause / perimenopause is one of the most underserved areas in consumer health and one where Bios's substrate is unusually well-positioned. The vasomotor symptom (VMS) signature — hot flashes / night sweats — is detectable on:

- **Skin temperature** ([SKIN_TEMPERATURE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L68), [SKIN_TEMPERATURE_DEVIATION](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L69)): brief +0.3–0.7°C deviations with sub-30-min recovery, especially overnight (Thurston 2011)
- **Heart rate**: brief tachycardia transient accompanying the flash (Carpenter 2007)
- **Sleep disruption**: [SLEEP_FRAGMENTATION_INDEX](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L87), [WAKE_AFTER_SLEEP_ONSET](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L88) — night-sweat-driven awakenings are the second most common menopausal complaint after the flashes themselves (SWAN study, Avis 2015)

NAMS 2022 Hormone Therapy Position Statement increasingly anchors decision-making to the perimenopausal window (typical age 45–55) and to symptom burden. The clinical reality is that most perimenopausal patients are not getting structured care — they're presenting to primary care with symptoms attributed to stress, depression, or "midlife" without any clinician anchoring the workup in reproductive endocrinology. A pull-side Bios surface — *the owner navigates in*, not pushed — that says "you are 47, your cycle log shows skipped cycles, hot-flash markers are detectable on your nighttime skin-temp/HR pattern, the standard staging labs are FSH + estradiol + AMH and your last results from N months ago show X" would be exactly the manifesto-aligned application of the architecture.

Concrete additions:

1. **`PhysiologyState.PERIMENOPAUSAL_TRANSITION` and `MENOPAUSAL`** — owner-asserted, gates patterns appropriately (HRV cycle correlation in [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L482) is no longer meaningful in true menopause; cycle-phase classification stops being emitted)
2. **`vasomotorPattern` in ConditionPatterns** — sub-30-min skin-temp + HR transients, recurring nightly, ≥3 per night sustained over ≥7 nights. Pull-side surface ("Bios is detecting a vasomotor pattern consistent with hot flashes — frequency and intensity log available"). Push-side stays silent unless owner has opted in
3. **`FSH`, `AMH` biomarker types** in [MetricType.kt](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt) — currently absent; `ESTRADIOL` is present. The full menopause-staging panel is FSH + estradiol + AMH (NAMS 2022). Reference ranges are age-dependent and lab-dependent; Bios stores raw values per the existing biomarker convention
4. **`menopause_management` pull-side surface** — owner-initiated, shows cycle log + vasomotor pattern + biomarker results + DEXA cadence + cardiovascular-risk reminder (post-menopause cardiovascular risk equalises to male peers within ~10 years — this is the relevant prevention pivot point for many owners)

### 2.7 Cycle tracking accuracy could be improved with multi-modal inference

[CycleInference.kt](../../android/app/src/main/java/com/bios/app/engine/CycleInference.kt) uses Marshall 1968 / Barron & Fehring 2005 biphasic 3-day BBT rule — clinically correct, conservative, but single-modality. The category leaders use:

| Tool | Inference inputs | FDA clearance |
|---|---|---|
| Natural Cycles | Oral BBT + cycle-length history + optional LH strip | K200158 (2018) — Class II, contraception indication |
| Clue | Cycle-length history + symptom logging | Not FDA-cleared for contraception |
| Flo | Cycle-length history + symptom logging + (premium) LH strip | Not FDA-cleared for contraception |
| Apple Cycle Tracking | Wrist skin temperature overnight + cycle log | Not FDA-cleared for contraception; explicitly disclaimed |

Bios already has: BBT entry, overnight skin temperature ([SKIN_TEMPERATURE_DEVIATION](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L69) from wearables), HRV phase variation (referenced in [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L483)), and cycle-length history (via [MENSTRUATION_ONSET](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L133) log). A multi-modal inference (wrist temp + HRV phase + cycle-length confidence + BBT when available) would improve ovulation detection without requiring an LH strip add-on. **Bios should not claim contraception indication** — that requires FDA clearance, which is a separate work item with separate risk surface. The manifesto-clean framing is "this is data on cycle phase, not a contraception aid; for fertility-awareness contraception use a clinically validated tool."

### 2.8 PCOS, endometriosis, adenomyosis

The three highest-prevalence gynecologic diagnoses have no first-class surface.

**PCOS** (Rotterdam 2003 criteria: 2 of 3 of oligo-/anovulation + clinical/biochemical hyperandrogenism + polycystic ovarian morphology on US). Bios substrate present: cycle irregularity via [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L475), insulin-resistance markers via [HOMA_IR](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L169) and [FASTING_INSULIN](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L168), [TESTOSTERONE_TOTAL](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L178). Missing: SHBG, free-androgen-index, DHEA-S; no `pcos_signature` pattern that combines them. Recommended addition: `pcos_signature` biomarker pattern in [BiomarkerConditionPatterns.kt](../../android/app/src/main/java/com/bios/app/alerts/BiomarkerConditionPatterns.kt) — elevated total testosterone *or* low SHBG (high free-androgen-index proxy) + elevated HOMA-IR + cycle-length irregularity logged. Suggested action: "discuss with your obstetric/gynecological provider; PCOS is a clinical diagnosis that combines biomarker and ultrasound findings."

**Endometriosis** (mean diagnostic delay 7–10 years across multiple cohorts — Nnoaham 2011, Hadfield 1996). The diagnostic delay is partly because the symptoms (cyclic pelvic pain, dyspareunia, dyschezia, infertility) are dismissed as "normal menstrual pain." Wearable-detectable substrate is limited (no specific biomarker), but the symptom-cycle correlation is exactly what a pain-diary + cycle-phase surface could support. Bios has [PAIN_SCORE](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L79) and `CYCLE_PHASE`; what's missing is a `pain_cycle_correlation` pull-side surface that visualises pain-score by cycle day across several cycles, with an explanatory hand-off ("if this pattern correlates strongly with menstruation and is interfering with daily function, gynaecological evaluation for endometriosis or adenomyosis is reasonable"). This is a manifesto-aligned application — Bios is the instrument, the owner takes the pattern to a provider, and the diagnostic delay shortens because the owner walks in with structured data instead of "I have bad cramps."

**Adenomyosis** — increasingly recognised on imaging in younger patients than the classical "multiparous women in their 40s" framing suggested. Presents as heavy menstrual bleeding + dysmenorrhea. The bleeding-quantification surface is absent in Bios (no `MENSTRUAL_FLOW_VOLUME` or PBAC-style log). Adding a flow-quantification entry under [PeriodEntryRepo](../../android/app/src/main/java/com/bios/app/data/PeriodEntryRepo.kt) — even a simple light/moderate/heavy categorical — would let the same `pain_cycle_correlation` surface highlight the heavy-bleeding subset.

### 2.9 No contraception annotation

Hormonal and non-hormonal contraception meaningfully shift signals Bios reads:

| Method | Signal effect | Pattern impact |
|---|---|---|
| Combined OCP (estrogen + progestin) | HRV ↓ 5–10%; BBT thermal shift abolished; cyclic mood/sleep shifts in placebo week | [recoveryDeficit](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L339) may false-fire; [CycleInference](../../android/app/src/main/java/com/bios/app/engine/CycleInference.kt) emits no OVULATORY/LUTEAL (silent — owner not informed why) |
| Progestin-only pill | Similar HRV depression, variable bleeding patterns | Similar to above |
| Hormonal IUD (LNG) | Often amenorrhea after 6–12 months; minimal systemic hormonal effect on HRV | [menstrualCycleAnomaly](../../android/app/src/main/java/com/bios/app/alerts/ConditionPatterns.kt#L475) may false-fire on missing onset logs |
| Copper IUD | Increased flow + dysmenorrhea first 6–12 months; no hormonal effect | Pain-pattern interpretation needs context |
| DMPA injection | Ovulation suppression, often amenorrhea, bone density concerns long-term | DEXA cadence consideration on long-term use; cycle inference silent |
| Implant (etonogestrel) | Irregular bleeding, generally suppressed ovulation | Cycle inference silent |
| Fertility-awareness | Requires precise cycle data — Bios is *exactly* the substrate, but should not claim contraception indication without FDA review | Use case calls for the most accurate possible cycle inference (§2.7) |
| Surgical sterilisation | No cycle suppression but no pregnancy risk | Cycle inference continues; pregnancy-related patterns silent on owner's known status |

A simple owner-asserted `CONTRACEPTION_METHOD` annotation surface — using the same `SELF_REPORTED` provenance the lab-value entry uses, and the same medication-annotation pattern primary-care audit §2.5 recommends — lets the pattern explanation builder de-mystify the silent cycle inference for OCP users, suppress mood-pattern false alarms in the placebo week for owners who want that, and gate fertility-awareness messaging appropriately.

### 2.10 Domestic violence and reproductive coercion threat-model alignment

This is where the manifesto and the post-Dobbs / DV-survivor threat models converge most clearly. Reproductive coercion (sabotaging contraception, forced pregnancy continuation, pregnancy-test policing) is a documented form of intimate-partner violence; the prevalence in IPV-experiencing populations is high (~25% in some studies — Miller 2010, *Contraception*). The relevant threat actors are: an intimate partner with intermittent device access (most common); a partner with primary device access who has installed Bios *for* the survivor (less common but exists); a state actor pursuing the survivor through a partner's reporting (rare but present in some jurisdictions post-Dobbs).

**Bios's existing posture is correct for this**:

- LETHE duress PIN — see [SafeMode.kt](../../android/app/src/main/java/com/bios/app/platform/SafeMode.kt) and [LetheCompat.kt](../../android/app/src/main/java/com/bios/app/platform/LetheCompat.kt) — destroys reproductive DB first ([DataDestroyer.kt:42](../../android/app/src/main/java/com/bios/app/platform/DataDestroyer.kt#L42))
- No notification side-channel that betrays reproductive tracking — [DisconnectDetector.kt:35](../../android/app/src/main/java/com/bios/app/alerts/DisconnectDetector.kt#L35) excludes reproductive sources by construction
- No exported summary contains reproductive data by default — FHIR exporter and PDF exporter both hard-skip

What is missing for the DV use case specifically:

1. **A "pregnancy in secret" mode** — the use case where an owner wants to track a pregnancy they cannot disclose. The current architecture supports it (the owner can set `PREGNANCY_T1/T2/T3` and Bios won't surface it on default screens), but it is not *documented* as a supported use case. A doc-only addition to [PRIVACY_ARCHITECTURE.md](../PRIVACY_ARCHITECTURE.md) acknowledging this use case would be appropriate — without making it discoverable in a way that creates a marketing surface
2. **Notification text discipline** — already correct per [AlertContentPolicy.kt](../../android/app/src/main/java/com/bios/app/alerts/AlertContentPolicy.kt), but a final pass through the OB-pattern alert text to ensure no notification body ever contains the word "pregnancy" or "cycle" or "ovulation" (the *channel* is fine; the *content* shown on a lock screen must be neutral). Recommended addition to [AlertContentPolicy.kt](../../android/app/src/main/java/com/bios/app/alerts/AlertContentPolicy.kt)'s CI-gated banlist for reproductive-domain pattern bodies
3. **`PhysiologyState` invisibility on shared-screen surfaces** — the Settings → Physiology state screen reveals the owner's chosen state to anyone with device access. A second PIN to view this screen (separate from the device PIN) would harden this — the same shape as the reproductive-DB passphrase

### 2.11 Gender-affirming care: transmasculine patients with retained anatomy

Transmasculine patients with retained female reproductive anatomy (uterus, cervix, ovaries, breast tissue depending on top-surgery status) still need cervical screening, breast-related considerations, and have pregnancy potential. Testosterone therapy does not eliminate pregnancy risk and does not eliminate cervical-cancer risk. ACOG Committee Opinion 823 (2021) explicitly addresses this; the screening cadences track to anatomy, not gender.

[ScreeningCatalog.kt:10-17](../../android/app/src/main/java/com/bios/app/screening/ScreeningCatalog.kt#L10-L17) explicitly notes "trans / non-binary owners pick whichever recommendation set matches their organ-system presentation; the catalog doesn't impose identity politics on cadence math" — engineering-defensible. But the UI labels in [PreventiveCareScreen.kt:367-368](../../android/app/src/main/java/com/bios/app/ui/screening/PreventiveCareScreen.kt#L367-L368) read "Female-bodied" / "Male-bodied", which is a binary gendered-body description that misses transmasculine-with-retained-anatomy owners and is awkward for intersex owners and inadequate for the two-spirit / third-gender / fourth-gender frames the [Indigenous Americas audit §2.6](INDIGENOUS_AMERICAS_POV.md) names.

The cleanest fix (also recommended by the Indigenous Americas audit): keep the anatomy-based logic, re-label the UI as direct anatomy questions — "Have breast tissue?" / "Have a cervix?" / "Have prostate / testes?" / "Could become pregnant?" Each answer feeds the catalog's `Applicability` directly without imposing a binary body description. Cost is small; correctness improvement is meaningful across multiple populations.

For HRT context specifically: testosterone therapy shifts HRV (variable direction in the literature), can shift sleep architecture, and shifts hematocrit upward (one of the monitored labs). A `GENDER_AFFIRMING_HRT` `PhysiologyState` (or annotation) would let the engine read these correctly, the same shape as the contraception annotation in §2.9.

### 2.12 Pregnancy loss and sensitive memory handling

Miscarriage (~10–20% of clinically recognised pregnancies; higher when biochemical losses included), stillbirth (~6 per 1000 in US), and termination — for medical or personal reasons — all leave a data footprint. The manifesto's "no judgement" applies critically here, and Bios's existing posture is correct: when the owner clears `PREGNANCY_T1/T2/T3` state, the patterns revert. But the *cycle and pregnancy-related readings* persist in the reproductive DB until the 90-day retention window elapses. Two recommendations:

1. **A specific "this pregnancy ended" workflow** — owner-initiated, optionally clears the pregnancy-related entries from the reproductive DB ahead of the retention window. No questions about cause; no logging of the event itself; just an offered acceleration of the wipe
2. **No anniversary notifications** — Bios doesn't currently surface anniversary content, but if any future calendar surface is added, pregnancy-related entries must not generate "one year ago today" reminders. Anniversary-of-loss notifications are a well-known antipattern in the consumer reproductive-health category

### 2.13 Fertility tracking and assisted reproduction (IVF / IUI)

REI use case: owners undergoing controlled ovarian hyperstimulation (COH) for IVF / IUI are tracking high-stakes data — follicle monitoring, estradiol trajectories, trigger timing. The single highest-acuity adverse event is ovarian hyperstimulation syndrome (OHSS), which can be life-threatening in severe form (hemoconcentration, third-spacing, thromboembolism). OHSS is wearable-detectable in late forms (resting tachycardia, weight gain from third-spacing detectable on [BODY_MASS](../../android/bios-contracts/src/main/kotlin/com/bios/contracts/MetricType.kt#L121) via Withings scale, decreased urine output is not wearable-detectable). A `ohss_screen` pattern gated on an owner-asserted `IVF_STIMULATION_ACTIVE` state — rapid weight gain + sustained tachycardia + (when symptoms entered) abdominal distention — surfaces the late warning. The early warning is the IVF clinic's job (estradiol levels, follicle counts via TVUS); Bios is the *late* / between-monitoring-visits safety net.

### 2.14 Maternal cardiac conditions (cross-reference cardiology audit)

Peripartum cardiomyopathy — see §2.3. Pulmonary hypertension in pregnancy carries 30–50% maternal mortality and is one of the absolute contraindications to pregnancy continuation; owners with known PAH should have been counselled pre-conception, but Bios is the appropriate watchful instrument during pregnancy if it occurs. Pre-existing congenital heart disease in pregnancy (Mauer / mWHO classification) has specific monitoring needs that overlap cardiology-audit territory; the Ob/Gyn lens is "trust the wearable signals for trend monitoring, escalate to MFM + cardio-obstetrics jointly for management."

## 3. Manifesto / clinical-ethics tension points

These are places where the manifesto and standard Ob/Gyn practice produce different answers; Bios should be aware which it chose.

### 3.1 "Never evaluate the person" vs. pregnancy-context risk communication

The manifesto's stance — Bios reports deviations, never evaluates — is correct and load-bearing. The friction point in obstetrics: pre-eclampsia is one of the conditions where the *magnitude* of risk genuinely matters. A patient with severe-range BP at 32 weeks with new headache + visual changes is not in the same risk class as a patient with stage-1 BP at 24 weeks with no other features. The clinical reality is "this is acute" vs. "this is something to bring up next visit."

The §2.1 `severityFloor = AlertTier.URGENT` mechanism is the manifesto-aligned way to express this: the *severity tier* communicates urgency without Bios "evaluating" the person. The text stays data-first ("severe-range BP in pregnancy is a hypertensive emergency — contact your obstetric provider or labor and delivery") and respects autonomy. This is the right resolution.

### 3.2 "Silence is a feature" vs. obstetric emergencies

Silence is correct for cycle-pattern trend notices. It is *incorrect* for BP 175/115 in a 34-week patient. The disconnect/Bios-state push admissibility carve-out in [AlertContentPolicy.kt](../../android/app/src/main/java/com/bios/app/alerts/AlertContentPolicy.kt) already establishes the framing — "failure is not silence." Severe-range BP in pregnancy is closer to the disconnect-notification category than to the trend-notice category. The URGENT escalation in §2.1 expresses this within the manifesto.

### 3.3 "Free to all" + "no Play Services" + the maternal mortality crisis

This is the place where the manifesto's architectural commitments and the public-health reality converge most powerfully. Maternal mortality in underserved US populations is principally an access problem. Bios runs on older Android, has no subscription tier, requires no Google account, works offline, and has no telemetry that could be subpoenaed. **The architecture that exists for personal-autonomy / LETHE reasons is the same architecture that is structurally well-placed for the maternal-mortality-crisis access gap.** This is worth saying out loud in [PRIVACY_ARCHITECTURE.md](../PRIVACY_ARCHITECTURE.md) alongside the existing GDPR / HIPAA / Dobbs framing — the same recommendation the [Indigenous Americas audit](INDIGENOUS_AMERICAS_POV.md) made about CARE / OCAP alignment.

### 3.4 Reproductive-data isolation vs. clinician share-out completeness

A patient handing their Ob/Gyn provider a Bios FHIR bundle for a *gynecological* visit currently gets a bundle that excludes reproductive data — because the default exporter hard-skips `WOMENS_HEALTH`. This is the correct default for every *non-gyn* hand-off, but for the gyn visit specifically the patient wants the cycle data included. The recommendation is a deliberate, secondary export path — "include reproductive data in this share-out" — that requires the reproductive-DB passphrase to unlock, and that produces a separate file the owner reviews before sharing. The default stays hard-skip; the unlock is owner-initiated, owner-passphrase-gated, and the file is reviewable before it leaves the device. This preserves the post-Dobbs threat model floor while letting the gyn-visit use case work.

**Do not adopt**

- **Algorithmic inference of pregnancy from cycle/BBT data.** The current "owner asserts state, Bios never infers" posture is *threat-model load-bearing*. An algorithmic pregnancy-detection feature in the main DB would create exactly the forensic signal the separate reproductive DB exists to avoid. The convenience win is not worth the architectural sacrifice. This is a non-negotiable
- **A "Bios fertility score" or composite reproductive-health number.** Same shape as the primary-care audit's "do not adopt biological age composite" — reductive composites push toward evaluation. The data-first framing (individual patterns, surfaced when asked) is correct
- **FDA contraception indication without a separate regulatory work plan.** Natural Cycles cleared K200158 in 2018 with substantial clinical-trial data; that's a multi-year, multi-million-dollar undertaking with a separate risk surface (false-negative ovulation detection → unintended pregnancy → patient harm). Bios should not informally drift into this claim space. Cycle inference for *awareness* is appropriate; contraception indication requires its own program
- **Default-on pregnancy-related notifications.** The owner should pull these surfaces in, not have them pushed. Anyone-with-device-access shouldn't learn the owner is pregnant from a notification

## 5. Summary line for the project

> Bios's separately-encrypted reproductive database — independent key in StrongBox-backed EncryptedSharedPreferences, independent destroy path with priority on LETHE duress PIN, FHIR and PDF exporters that hard-skip WOMENS_HEALTH at the type level, baselines computed in-memory so the reproductive DB never leaks raw values into the main DB — is the most institutionally remarkable single feature in any consumer reproductive-health product I have audited, and is the right architecture for a post-Dobbs threat model in which period-tracker data has already been used in criminal prosecution. The Ob/Gyn lens recommends (a) a pregnancy-specific pre-eclampsia signature that reuses the existing BP ingestion, `PhysiologyState`, and `severityFloor = URGENT` mechanism; (b) completing the pregnancy gating that has been built but not wired across the patterns it would silence; (c) postpartum replacement patterns targeting the highest-mortality six-week window; (d) anatomy-anchored screening labels in place of the binary "female-bodied / male-bodied" language; and (e) naming the architectural alignment with maternal-mortality-crisis access gaps and DV-survivor reproductive-coercion threat models in the privacy documentation. None of these dilute the reproductive-data isolation floor; all of them are within the existing architecture and within the manifesto.
